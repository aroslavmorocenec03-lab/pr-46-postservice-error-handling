# Звіт до практичної роботи №46

**Тема:** обробка помилок у клієнтському застосунку: PostServiceClient та глобальний обробник.

**Мета:** розділити серверну комунікацію й інтерфейс, обробляти відновлювані помилки локально та завершувати застосунок з діагностикою після непередбачених збоїв.

## Виконана робота

Створено інтерфейс `IPostServiceClient` і реалізацію `PostServiceClient` для п’яти ендпойнтів `/postings`. Клас виконує HTTP-запити, перевіряє відповіді в одному `EnsureSuccessAsync` і десеріалізує DTO. Клас `PostingValidationException` переносить словник помилок полів для відповіді 400. Решта HTTP-помилок містить `StatusCode` у стандартному `HttpRequestException`.

Форми використовують інтерфейс клієнта. Валідація залишає редактор відкритим, відсутній запис спричиняє оновлення списку, а тимчасовий збій пропонує повтор або скасування. Загальний `catch (Exception)` у формах відсутній. Стан кнопок відновлюється у `finally`.

У `Program.cs` підключено глобальні події `AppDomain.CurrentDomain.UnhandledException` та `Application.ThreadException`. Діагностика містить час, тип, повідомлення, повний виняток, вкладені винятки й стек. Для асинхронних подій UI використовується шлях `ThreadException`, після повідомлення виконується `Application.Exit()`.

## Перевірка HTTP через .rest

Файл `requests/postservice.rest` виконано сценарієм `scripts/Invoke-Rest.ps1`; фактичні відповіді збережено в [rest-results.txt](rest-results.txt). Перевірено 200 для списку, 404 для відсутнього запису, 400 зі словником `errors`, справжній серверний виняток 500 та повернення до 200 після вимкнення навчальної помилки.

Після зупинення тестового сервера повторно виконано `requests/server-stopped.rest`. Запит не отримав HTTP-відповіді й завершився тайм-аутом 3 секунди — це реальний результат цього запуску, а не HTTP 500. Запис збережено в [offline-rest.txt](offline-rest.txt).

## Чому у формах обробляються не всі помилки

Локальний обробник повинен мати дію, після якої стан програми зрозумілий. При 400 користувач може виправити поля, при втраті зв’язку — повторити запит, при 404 окремого запису — отримати актуальний список. Для 500 або порушення JSON-контракту такого виправлення у формі немає. Приховування винятку залишило б застарілі дані й невідомий стан. Тому він доходить до глобального обробника, який фіксує подробиці, пояснює збій користувачеві й завершує роботу.

## Відповіді на контрольні запитання

1. **Які групи помилок виникають при виклику сервера?** Втрата мережі або недоступний сервер — `HttpRequestException` без `StatusCode`; HTTP-помилка — виняток із відповідним статусом; 400 із правилами валідації — `PostingValidationException`; неправильний вміст успішної відповіді — `JsonException`; тайм-аут `HttpClient` — зазвичай `TaskCanceledException`.
2. **Чому не можна однаково реагувати на недоступність, валідацію та 500?** Тимчасовий збій дозволяє повтор, валідація потребує зміни даних, а 500 вимагає діагностики й виправлення сервера або програми. Однакове повідомлення не дає користувачеві правильної дії.
3. **Чому перехоплюють лише винятки з відомою реакцією?** Лише тоді можна обґрунтовано продовжити роботу. Решта винятків передається вище до глобальної обробки. Якщо після власних дій потрібно передати виняток далі, застосовують `throw;`, щоб зберегти початковий стек.
4. **Що вирішує PostServiceClient?** Адреса сервера, `HttpClient`, JSON і перевірка статусів зосереджені в одному місці. Форми не дублюють транспортний код, працюють із DTO та зрозумілими винятками. Контракт видно через `IPostServiceClient`.
5. **Як відрізняються GetFromJsonAsync та GetAsync?** Перший сам перевіряє успішність HTTP й читає JSON; неуспішний статус перетворюється на виняток. `GetAsync` повертає `HttpResponseMessage`, тому клієнт має явно перевірити статус і може спочатку прочитати тіло з помилками.
6. **Навіщо власний PostingValidationException?** Він переносить структурований словник повідомлень за полями, потрібний редактору. Для інших неуспішних відповідей достатньо `HttpRequestException.StatusCode`, за яким можна обрати реакцію через `when`.
7. **Чому порожній catch або загальний catch у формі небезпечні?** Вони можуть приховати помилку без виправлення стану. Користувач бачить порожню або застарілу таблицю, а розробник не отримує діагностику. У цій роботі форми ловлять конкретні відновлювані випадки, а непередбачені помилки не поглинають.
8. **Що стається після глобального UnhandledException і навіщо він потрібен?** Для необробленого фатального винятку він не повертає застосунок до нормальної роботи. Його призначення — остання діагностика й зрозуміле повідомлення перед завершенням. Для UI-події `Application.ThreadException` завершення в цьому проєкті виконується явно; продовжувати роботу після невідомого збою не пропонується.

## Висновок

Клієнт відокремлює HTTP від форм, передає серверні помилки валідації, розрізняє збої за типом і статусом, підтримує повтор та виправлення даних. Глобальна обробка фіксує непередбачені помилки й завершує застосунок зі зрозумілим повідомленням. Поведінку перевірено автоматично та в реальному Windows-інтерфейсі.
